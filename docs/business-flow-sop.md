# TBM-MES 单项目全流程跑通 SOP 与数据准备清单

**适用系统**：factory-mes（自研 MES）  
**部署地址**：https://192.168.1.73  
**文档版本**：v1.0  
**编制日期**：2026-10-20  
**适用范围**：TBM-2026-001（郑州地铁 4 号线 4m 盾构机）为首个试点项目，走通后复制到其它项目

---

## 一、这份 SOP 要解决什么问题

系统功能已经够用（63 个业务页面、8 个只读 MCP 工具、OEE/追溯/成本三层差异均可用），当前主要矛盾不是功能缺失，而是两件事：

1. **数据厚度不够**：BOM 68 行里只有 8 行挂了实装批次；3 张工单只有 1 条报工；序列号 0；文档 0；成本台账只有人工一类。
2. **流程责任没落到人**：没人负责每天把工单、报工、检验、领料推进一格，系统就不会自己长出数据。

本 SOP 的目标很具体：**把 TBM-2026-001 的「全流程健康检查」分数从 56.3（流程阻塞）提升到 85 分以上（流程健康）**，并把每天要做的动作固定下来。

> 健康检查入口：仪表盘 `/dashboard` 顶部「全流程健康检查」卡片；接口 `GET /api/dashboard/process-health?instance_id=1`。

### 1.1 验收标准（三个阶段）

| 阶段 | 健康分 | 判定 | 业务含义 |
|---|---|---|---|
| 起步 | < 60 | 流程阻塞 | 数据不足以支撑排程/成本/追溯 |
| 可跑 | 60 ~ 84 | 部分可跑 | 主流程能走，个别环节缺数据 |
| 跑通 | ≥ 85 | 流程健康 | 8 个环节都有数据，可出经营报表 |

### 1.2 每日五个闭环指标（最重要）

| 指标 | 在哪看 | 每天最少 |
|---|---|---|
| 工单状态推进数 | `/work-orders` | 1 张 |
| 报工条数（含工时） | `/process-hours`、`/scan` | 按当班工序数 |
| 检验记录数 | `/quality` | 1 条 |
| 领料流水数 | `/materials`、`/kit-closure` | 按领料单 |
| 文档上传数 | `/documents` | 每周 ≥ 1 |

> 这五个数不动，流程就是没跑起来——跟系统有多少页面无关。

## 四、八个环节操作 SOP

### 4.1 环节一：项目与里程碑（责任：PM / 计划）

**目标**：项目信息完整，里程碑可跟踪。

**页面**：`/project-wizard`（新项目）、`/instances`（项目列表）、`/instances/:id`（详情）

**必填字段**：实例编码、名称、客户、合同号、合同金额、计划开工/完工、里程碑（阶段+计划日期）

**操作步骤**：
1. 新项目走 `/project-wizard`，按向导填客户/合同/机型/里程碑；
2. 已有项目在 `/instances/:id` 补合同号、客户、现场位置（进度由系统自动回写，不用填）；
3. 里程碑逐条确认计划日期，逾期里程碑在 `/delivery` 看红；
4. 进度由系统按「工序完成率（标准工时加权）」自动回写 —— 工单/工序状态一变就更新，无需人工推进。

**验收标准（健康检查 ok）**：里程碑 ≥ 1 且合同号已填。

**常见卡点**：
- 合同号为空 → 健康检查标"部分"，成本与交付统计缺依据；
- 进度一直 0% → 说明工序/工单没有状态变化；先确认工序已建、状态在流转，必要时点「重算进度」。

---

### 4.2 环节二：设计与 BOM（责任：技术 / 仓库）

**目标**：BOM 每一行都有物料，主要物料行挂上实装批次——这是量差、追溯、成本的基础。

**页面**：`/bom`、`/eco`、`/documents`（图纸）

**必填字段**：物料编码、名称、数量、层级（L1~L4）、**实装批次**、供应商

**操作步骤**：
1. 打开 `/bom` 选项目，检查"挂物料"与"挂实装批次"两列；
2. 装配/工艺节点（无物料的 39 行）确认是否应保持为空；能补物料的补上；
3. 用导入工具批量挂批次：
   - 生成模板：`node scripts/gen-backfill-templates.js --type=bom-lots --only-linkable`
   - 试运行：`node scripts/data-backfill.js --type=bom-lots --csv=...`
   - 正式导入：`--apply`（写前自动检查备份）
4. BOM 变更走 `/eco`，不要直接改历史行。

**验收标准（健康检查 ok）**：BOM 行 ≥ 1、挂物料 ≥ 1、实装批次覆盖 ≥ 80%。

**常见卡点**：
- 只有 BOM 结构没有物料 → 健康检查"部分"；
- 批次覆盖率 < 80% → 量差算不出来（会进 `not_computed`）。

---

### 4.3 环节三：工艺树与排程（责任：计划 / 工艺）

**目标**：工序有工位、有计划时间、有依赖，排程结果可信。

**页面**：`/process-tree`、`/process-master`（工序/岗位配置）、`/process-params`（工艺参数）、`/process-hours`（工时与报工）、`/multi-schedule`、`/gantt`、`/schedule`

**必填字段**：工序名称、所属工位、标准工时、计划开始/结束、前置工序、工艺参数

**操作步骤**：
1. `/process-tree` 按项目检查工序树：缺工位的挂工位，缺计划时间的补计划；
2. `/process-master` 维护工序主数据与工位能力（班次时长、人数）；
3. `/process-params` 填关键工艺参数（推力、扭矩、注浆压力等）；
4. `/multi-schedule` 跑多项目资源平衡，看热力图：红色格子说明超载，可拖动改派；
5. `/gantt` 看单项目甘特，确认关键路径。

**验收标准（健康检查 ok）**：工序 ≥ 1、全部有工位、计划时间覆盖 ≥ 80%。

**常见卡点**：
- 工序没计划时间 → 甘特排不出来；
- 工位日能力配置过大（如 24h）→ 负荷热力图偏乐观，需在 `/workstation-resources` 核对班次×人数。

---

### 4.4 环节四：派工与报工（责任：车间 / 操作工）

**目标**：每张工单都派到工位和人，每天有实际工时——这是 OEE、效率差、进度的事实基础。

**页面**：`/work-orders`、`/shopfloor`、`/scan`、`/process-hours`

**必填字段**：工单号、工位、负责人、计划起止、实际起止、实际工时、完成数量

**操作步骤**：
1. `/work-orders` 建单或导入，状态推进（待派工 → 已派工 → 进行中 → 完成）；
2. 派工：选工位与人（`PUT /api/work_orders/:id/dispatch`）；
3. 操作工在 `/scan` 扫码开工，或在 `/shopfloor` 点"开始/完工"；
4. 完工后填实际工时（关键！`/process-hours`），一张工单至少一条报工；
5. 异常在 `/andon` 呼叫，处理结果来自 `/exceptions`。

**验收标准（健康检查 ok）**：工单 ≥ 1、已派工位、报工覆盖 ≥ 工单数。

**常见卡点**：
- 只派工不报工 → 效率差进 `not_computed`，OEE 性能不可信；
- 报工覆盖 1/3 → 健康检查"部分"，明确提示"报工只覆盖 1/3 张工单"。

---

### 4.5 环节五：齐套与领料（责任：仓库 / 计划）

**目标**：物料齐套可查、领料有流水、关键件能追到序列号。

**页面**：`/kit-closure`、`/materials`、`/purchase`、`/material-alerts`、`/critical-parts`

**必填字段**：物料编码、批次号、数量、库位、领料工单、序列号、供应商

**操作步骤**：
1. `/materials` 登记批次（供应商、到货日期、数量、质检状态）；
2. `/kit-closure` 按工单跑齐套检查，缺料项在 `/material-alerts` 看预警；
3. 领料：扫码或手工出库，生成领料流水（`material_movements` type=issue）；
4. 关键件（主轴承、刀盘、密封等）在 `/critical-parts` 绑定序列号；
5. 每周核对库存与实物，差异走盘点。

**验收标准（健康检查 ok）**：领料流水 ≥ 1 且序列号 ≥ 1。

**常见卡点**：
- 有批次无领料 → 量差算不出来；
- 序列号 0 → 追溯只能到批次（L4 断点）。

---

### 4.6 环节六：检验与证据（责任：质检）

**目标**：来料/过程/出厂检验有记录，焊缝有 NDT，装配有过程记录。

**页面**：`/quality`、`/spc`、`/tbm-advanced`（焊缝/NDT/装配）、`/documents`

**必填字段**：检验类型、检验项目、判定结果、检验员、时间、附件（照片/报告）

**操作步骤**：
1. `/quality` 维护检验模板，按工单创建检验单；
2. 过程检验按工序挂检验点，结果直接进 `/spc` 控制图；
3. 焊缝：在 `/tbm-advanced` 登记焊缝编号、焊工、参数；
4. NDT：超声/射线报告关联焊缝编号，结论写合格/不合格；
5. 不合格品走 NCR 流程，关闭后回到 `/quality` 看闭环。

**验收标准（健康检查 ok）**：检验 ≥ 1 且（NDT ≥ 1 或工单检验 ≥ 1）。

**常见卡点**：
- 有焊缝无 NDT → 健康检查"部分"，追溯链 L5 缺证据；
- 检验记录不挂工单 → 驾驶舱质检合格率统计不到。

---

### 4.7 环节七：文档与图纸（责任：文控 / 技术）

**目标**：图纸、SOP、合格证可上传、可追溯、可下载。

**页面**：`/documents`、`/plm`、`/eco`

**必填字段**：文档标题、文档编码、类型、版本、关联装备（必填）、关联 BOM 节点/ECO、文件

**操作步骤**：
1. `/documents` → 上传文档：选文件 → 填标题/编码/类型/版本 → **选关联设备（必填）** → 可选关联 BOM 节点；
2. 图纸类建议同时关联 BOM 节点，这样从 BOM/ECO 能直接追溯到最新版图纸；
3. 修改走新版本，不要覆盖旧版本（版本抽屉可对比历史）；
4. 下载为带鉴权的 blob 下载，中文文件名不会乱码。

**验收标准（健康检查 ok）**：关联到该项目的文档 ≥ 1。

**常见卡点**：
- 未选关联设备 → 提交时提示"请选择关联设备"（库上该字段 NOT NULL）；
- 标题含中文 → 已修复（header 编码），如仍报错请反馈。

---

### 4.8 环节八：交付与成本（责任：PM / 财务）

**目标**：交付/验收有里程碑，成本台账≥2 类，成本三层差异能算。

**页面**：`/delivery`、`/cost`、`/cost-variance`、`/outsourcing-depreciation-cost`、`/business-reports`

**必填字段**：成本类型（material/labor/outsourcing/depreciation/rework/quality_loss）、金额、发生日期、摘要、来源单据

**操作步骤**：
1. `/delivery` 维护交付批次与验收节点；
2. 成本台账用导入工具：`cost-entries.csv`（材料/人工/外协/折旧/返工/质量损失）；
   - 生成模板：`node scripts/gen-backfill-templates.js --type=cost-entries`
   - 试运行 → `--apply` 导入
3. `/cost-variance` 看三层差异（量差/价差/效率差）+ 台账核对；
4. 未领料/未报工的部分会进 `not_computed`，不要当成"节约"；
5. `/business-reports` 出经营分析报表。

**验收标准（健康检查 ok）**：交付里程碑 ≥ 1 且成本类型 ≥ 2。

**常见卡点**：
- 台账只有人工 → 健康检查"部分"，外协/折旧成本缺失；
- 材料未领料却要看量差 → 系统会明确标注未计入。

## 七、周会：用健康检查开会（30 分钟）

1. 打开 `/dashboard` → 「全流程健康检查」→ 选试点项目；
2. 念分数：本周 X 分（上周 Y 分），`已通 A / 部分 B / 未开始 C`；
3. 逐条过"部分/未开始"环节的**卡点文案**（都是具体数字）；
4. 每个卡点认领：责任角色 + 完成日期；
5. 只解决卡点，不在会上讨论功能需求；
6. 会后更新本 SOP（有新页面/新规则就补进去）。

## 八、异常处理与回滚

| 场景 | 处理 |
|---|---|
| 导入前 | 必须先 dry-run 看"将写入 N 处变更 / 跳过 / 错误"；错误行会指出行号 |
| 导入前备份 | `bash scripts/backup-db.sh`（写前自动检查最近备份 < 6 小时） |
| 导入出错 | `node scripts/data-backfill.js --rollback=data/backfill/batch-<时间戳>-<type>.json` |
| 批量数据搞脏 | 用边车文件回滚；不要手工 DELETE |
| 上传失败 | 提示"请选择关联设备"= 没选设备；"文件超过 50MB"= 需压缩 |
| 下载 401 | 已改为带 Authorization 的 blob 下载，需强刷浏览器（Ctrl+Shift+R） |
| 健康分异常波动 | 看 `/api/dashboard/process-health?instance_id=1` 的 metrics 原始计数 |
